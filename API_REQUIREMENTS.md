# ECOTWIN Simulation API Requirements

This document defines the API requirements for connecting the ECOTWIN UI to real model inference without making the inference service know about PocketBase.

The required shape is a layered integration:

1. **UI + PocketBase application layer**: owns records, cached files, routes used by the current frontend, and UI-specific result DTOs.
2. **Simulation orchestrator / adapter layer**: translates ECOTWIN application data into model-ready inputs, calls inference, and translates model output back to the UI contract.
3. **Inference API**: runs the model from model-ready inputs only. It must not know about PocketBase collections, record fields, file fields, or UI cache behavior.

The middle layer can be implemented inside PocketBase custom routes, as a separate service called by PocketBase, or as a service that calls PocketBase through its API. The key rule is that the inference API stays independent.

## Boundary Rules

The inference API must not receive or depend on:

- PocketBase collection names such as `simulations`, `managementPlans`, `tasks`, `tiles`, `landcovers`, or `oceanData`.
- PocketBase field names such as `resultJson`, `resultNpz`, `inputJson`, `simulationId`, or `status`.
- PocketBase record lifecycle semantics.
- PocketBase file URLs or cache paths.
- UI route names such as `/simulation/{recordId}/run`.

The inference API may receive:

- Model input rasters and masks.
- Model and agent selectors.
- Grid, time, species, and pressure/event parameters.
- Opaque run IDs generated by the orchestrator.
- Opaque activity IDs, only for tracing and diagnostics.

## Current UI Contract

The current frontend expects the application layer to keep this behavior:

1. The UI creates a PocketBase `simulations` record with `plan`, `options`, and `status: "pending"`.
2. The UI calls `GET /simulation/{simulationRecordId}/run?format=base64`.
3. The application layer eventually returns a `SimulationResultBase64` JSON object.
4. The application layer updates the `simulations` record:
   - `status: "running"` while executing.
   - `inputJson` with the normalized management plan snapshot.
   - `simulationId` with the orchestrator or inference run ID.
   - `resultJson` with the cached base64 result file.
   - `resultNpz` with the cached NPZ result file when requested.
   - `status: "completed"` on success or `failed` on error.

The UI considers a simulation completed if `status === "completed"` or a cached `resultJson` / `resultNpz` exists.

For least UI churn, keep the existing PocketBase route:

```text
GET /simulation/{simulationRecordId}/run
```

This route may call the orchestrator, but it should not call raw inference directly unless it first translates the input into the pure inference contract described below.

## Orchestrator Responsibilities

The orchestrator is the only layer that should understand both ECOTWIN application data and model inference data.

Required responsibilities:

- Load or receive the simulation record, linked management plan, linked tile, task list, landcover raster, and depth raster.
- Validate application data before inference.
- Normalize management plan activities into a stable application snapshot for `simulations.inputJson`.
- Derive time defaults:
  - `max_steps` from management-plan date range when not explicitly provided.
  - `sample_every` to keep playback frame count reasonable.
  - `tick_duration_days`, `start_date`, and `end_date` for UI labels.
- Generate polygon activity masks or convert polygons to model coordinates.
- Translate ECOTWIN activity types into model pressures/events.
- Choose model/agent configuration from user options.
- Call the pure inference API.
- Validate inference output.
- Convert inference output into the UI `SimulationResultBase64` format.
- Cache or return enough data for PocketBase to cache result files.

The orchestrator may store temporary uploaded files, intermediate run IDs, and mapping tables, but those are internal to the orchestrator.

## Application-Facing Endpoints

### `GET /simulation/{simulationRecordId}/run`

Primary application endpoint. It resolves the PocketBase simulation record, translates linked ECOTWIN data into a model-ready request, calls `POST /v1/runs` on the inference API, caches the returned UI result, and returns the UI result DTO.

Supported query parameters:

- `format`: `base64` is required. `npz` is optional.
- `worldSize` / `world_size`
- `maxSteps` / `max_steps`
- `sampleEvery` / `sample_every`
- `includeFinal` / `include_final`
- `tickDurationDays` / `tick_duration_days`
- `startDate` / `start_date`
- `endDate` / `end_date`
- `runs` / `runCount` / `run_count`
- `agentSet` / `agent_set` / `agent` / `agents`
- `modelPath` / `model_path`

The response for `format=base64` must be `SimulationResultBase64`.

### `GET /simulate/agents`

Application-facing model list endpoint. It maps inference `GET /v1/models` responses into the shape the current UI can consume.

Response:

```json
[
  {
    "name": "model-set-name",
    "kind": "single",
    "files": ["10_$codfish_9079.34.npy.npz"],
    "species": ["codfish"],
    "modelPath": "optional/path"
  }
]
```

If model discovery is not implemented, return `[]`.

## ECOTWIN Options Payload

The orchestrator may receive this payload from PocketBase. It must translate it before calling inference.

Common top-level keys:

- `max_steps` / `maxSteps`
- `sample_every` / `sampleEvery`
- `tick_duration_days` / `tickDurationDays`
- `world_size` / `worldSize`
- `age_groups` / `ageGroups`
- `age_step_interval` / `ageStepInterval`
- `agent`, `agentSet`, `agent_set`, `modelPath`, `model_path`
- `disabledTaskIds` / `demoDisabledTaskIds`
- `activityImpacts` / `demoActivityImpacts`
- `scenario`, `demoCacheKey`, `demoPlanTaskSignature`, `years`, `runs`
- `managementPlan`

Unknown keys must be accepted and ignored by the orchestrator.

Supported ECOTWIN activity types:

- `fishing`
- `construction`
- `windFarm`

- `constant`: applies across the whole simulation.

Supported target scopes:

- `wholeTile`: activity affects the full tile.
- `polygon`: activity affects supplied polygon geometry and uploaded masks.

Species IDs currently used by the UI:

- `phytoplankton`
- `zooplankton`
- `pelagicFish`
- `codfish`
- `porpoises`
- `seabirds`

The orchestrator should map these application species IDs to model species IDs if the inference model uses different names.

## Orchestrator Area Masks

For polygon activities, the orchestrator can receive or generate masks.

`area_masks_manifest` shape:

```json
[
  {
    "activityId": "TASK_RECORD_ID",
    "activityName": "Activity name",
    "activityType": "trawlArea",
    "areaIndex": 0,
    "fieldName": "area_masks",
    "fileName": "area_mask_01_01.png",
    "width": 100,
    "height": 100
  }
]
```

The orchestrator must translate masks into the inference input as model masks with model-local IDs. The inference API should not need activity names, PocketBase task IDs, or area summaries to interpret masks.

## Pure Inference API

The pure inference API should expose model-oriented endpoints. Suggested route names are below; exact names can differ as long as the contract stays model-oriented.

### `GET /health`

Recommended readiness endpoint.

```json
{ "ok": true }
```

### `GET /v1/models`

Recommended model discovery endpoint.

Response:

```json
[
  {
    "id": "baltic-default",
    "name": "Baltic default",
    "kind": "agent_set",
    "species": ["phytoplankton", "zooplankton", "pelagicFish", "codfish", "porpoises", "seabirds"],
    "supports_age_groups": false,
    "files": ["10_$codfish_9079.34.npy.npz"]
  }
]
```

The orchestrator maps this response into `GET /simulate/agents` for the UI.

### `POST /v1/runs`

Creates and runs, or creates and queues, a model inference run.

Two execution modes are acceptable:

- **Synchronous**: returns a completed model result in the response.
- **Asynchronous**: returns `202 Accepted` with a `run_id`, then the orchestrator polls `GET /v1/runs/{run_id}` until completion.

The current UI path is synchronous from the user's perspective. If the inference API is async, the orchestrator must hide that by polling or by updating PocketBase status in the background.

Request: `multipart/form-data`

Required fields:

- `request`: JSON `ModelRunRequest`.
- `texture`: model-ready raster file.
- `depth`: model-ready depth raster file.

Optional fields:

- `mask`: repeated raster mask files referenced by `request.pressures[].scope.mask_id`.

`ModelRunRequest`:

```json
{
  "run_id": "orchestrator-generated-run-id",
  "model": {
    "id": "baltic-default",
    "agent_set": "optional-agent-set",
    "model_path": "optional-model-path"
  },
  "grid": {
    "width": 50,
    "height": 50,
    "bbox": [11.1, 57.7, 11.2, 57.8],
    "coordinate_system": "EPSG:4326"
  },
  "time": {
    "max_steps": 365,
    "sample_every": 4,
    "include_final": true,
    "tick_duration_days": 1,
    "start_date": "2026-01-01",
    "end_date": "2027-01-01"
  },
  "species": ["phytoplankton", "zooplankton", "pelagicFish", "codfish", "porpoises", "seabirds"],
  "pressures": [
    {
      "id": "activity-1",
      "type": "fishing_effort",
      "time_window": { "start_step": 0, "end_step": 365 },
      "scope": { "kind": "mask", "mask_id": "mask-activity-1" },
      "parameters": {
        "species_effort_multipliers": {
          "codfish": 0.8
        }
      }
    }
  ],
  "output": {
    "dtype": "float32",
    "tensor_order": "frame,row,column,species",
    "include_summary": true,
    "summary_normalization": "relative_to_initial",
    "replicates": 20
  }
}
```

Required inference request behavior:

- Treat `run_id` and pressure IDs as opaque identifiers.
- Ignore unknown request keys.
- Validate grid dimensions, time settings, model selector, and species.
- Do not dereference application or PocketBase IDs.
- Return finite non-negative biomass values.

### `GET /v1/runs/{run_id}`

Required only if the inference API is asynchronous.

Queued/running response:

```json
{
  "run_id": "orchestrator-generated-run-id",
  "status": "running",
  "progress": 0.42
}
```

Completed response:

```json
{
  "run_id": "orchestrator-generated-run-id",
  "status": "completed",
  "result": {}
}
```

Failed response:

```json
{
  "run_id": "orchestrator-generated-run-id",
  "status": "failed",
  "error": {
    "code": "MODEL_FAILED",
    "message": "Human-readable explanation"
  }
}
```

## Inference Result Contract

The inference result should be easy for the orchestrator to map into the UI result DTO.

```json
{
  "run_id": "orchestrator-generated-run-id",
  "world_size": 50,
  "species": ["phytoplankton", "zooplankton", "pelagicFish", "codfish", "porpoises", "seabirds"],
  "sample_every": 4,
  "include_final": true,
  "tick_duration_days": 1,
  "start_date": "2026-01-01",
  "end_date": "2027-01-01",
  "dtype": "float32",
  "shape": [4, 50, 50, 6],
  "steps": [0, 120, 240, 365],
  "fitness": 1234.5,
  "episode_length": 365,
  "end_reason": "completed",
  "biomass_b64": "base64_encoded_float32_tensor",
  "summary": {
    "run_count": 20,
    "confidence_level": 0.95,
    "ci_method": "t-interval",
    "normalization": "relative_to_initial",
    "grouping": "functional_group",
    "steps": [0, 120, 240, 365],
    "groups": ["Phytoplankton", "Zooplankton"],
    "group_species": [["phytoplankton"], ["zooplankton"]],
    "mean": [[1, 1.05, 1.1, 1.12], [1, 0.98, 0.95, 0.94]],
    "ci_low": [[1, 1.01, 1.02, 1.03], [1, 0.94, 0.9, 0.88]],
    "ci_high": [[1, 1.09, 1.18, 1.2], [1, 1.02, 1.0, 1.01]]
  }
}
```

Tensor requirements:

- `dtype` must be `float32`.
- `shape` must be `[N, H, W, S]`.
- `steps.length` must equal `N`.
- `species.length` must equal `S`.
- `biomass_b64` must decode to `N * H * W * S * 4` bytes.
- Tensor order must be C-order `[frame][row][column][species]`.
- `steps` must be sorted ascending and correspond to tensor frames.
- Values must be finite and non-negative.
- The final tensor axis order must exactly match the `species` array.

Required UI fields:

- `simulation_id`
- `world_size`
- `species`
- `sample_every`
- `include_final`
- `dtype`
- `shape`
- `steps`
- `fitness`
- `episode_length`
- `biomass_b64`

Strongly recommended UI fields:

- `tick_duration_days`
- `start_date`
- `end_date`
- `end_reason`
- `biomass_summary`

The UI uses the result as follows:

- Map overlay decodes `biomass_b64`, uses `shape`, `species`, and selected frame.
- Timeline uses `steps`, `episode_length`, `start_date`, `end_date`, and `tick_duration_days`.
- Biomass chart prefers `biomass_summary`; otherwise it aggregates the tensor.
- Report page compares initial and final tensor frames.

## Optional NPZ Output

The current UI result view requires `format=base64`. NPZ is optional for downloads and Python workflows.

If the orchestrator exposes `format=npz`, return `application/octet-stream` containing:

- `biomass`: `float32` shaped `(N, H, W, S)`
- `steps`: `int32` shaped `(N,)`
- `species`: string array shaped `(S,)`
- `world_size`: `int32` shaped `(1,)`
- `sample_every`: `int32` shaped `(1,)`

## Error Contract

Use clear HTTP statuses at both orchestrator and inference boundaries:

- `400`: invalid request, bad options, missing files, invalid model selector.
- `404`: unknown run ID.
- `409`: model/input state conflict.
- `422`: valid JSON but unsupported simulation input.
- `500`: unexpected service failure.
- `503`: model service unavailable or overloaded.

Error responses should be JSON:

```json
{
  "error": "Short machine-readable code",
  "message": "Human-readable explanation",
  "details": {}
}
```

The orchestrator should map inference errors to UI-useful errors and set the PocketBase `simulations.status` field to `failed`.

## Performance And Size Limits

- Current PocketBase result file fields allow about 200 MB per cached result file.
- Base64 expands raw tensor bytes by about one third, plus JSON overhead.
- Keep `N * H * W * S * 4` comfortably below the cache limit. A practical target is under 100 MB raw tensor data.
- Return sampled frames only. Do not return every internal model step unless the sample count is intentionally small.
- Prefer `biomass_summary` for charting so the UI does not need to aggregate large tensors repeatedly.
- If inference can exceed 10 minutes, use an async inference API and have the orchestrator poll or run in the background.

## Acceptance Checklist

The integration is UI-compatible and inference-decoupled when all of these pass:

- The UI can still call `GET /simulation/{simulationRecordId}/run?format=base64`.
- The inference API does not receive PocketBase collection names, field names, file URLs, or record lifecycle instructions.
- The orchestrator translates ECOTWIN `managementPlan` data into a model-ready `ModelRunRequest`.
- `GET /simulate/agents` returns `200` and a JSON array mapped from inference `GET /v1/models`.
- The orchestrator can run a simulation from texture, depth, options, and optional masks.
- The UI-facing response includes all required `SimulationResultBase64` fields.
- `shape[0] === steps.length`.
- `shape[3] === species.length`.
- Decoded `biomass_b64` byte length equals `N * H * W * S * 4`.
- Biomass values are finite and non-negative.
- `start_date`, `end_date`, and `tick_duration_days` are preserved when supplied.
- PocketBase simulation status and cached result fields are updated by the application/orchestrator layer, not by inference.
- The tile page can render the map overlay, species toggles, timeline, biomass chart, and report.
- An asymmetric test tensor appears in the expected map orientation.

## Open Design Decisions

These do not block the contract, but should be decided before implementation:

- Whether the orchestrator lives inside PocketBase routes or as a separate service.
- Whether inference runs synchronously or asynchronously.
- Whether rasters are sent to inference as multipart files, object-store references, or preprocessed arrays.
- The canonical mapping from ECOTWIN activity types to model pressure types.
