ECOTWIN Cleanup Report

This report identifies placeholder/demo UI and disconnected workflow pieces that should be removed or finished before the project moves from prototype to cohesive application.

Scope: frontend, PocketBase, services, repo hygiene Primary gap: management plan data is not used by simulations Output target: PDF-capable simulation reports

Target Flow

Create and view tiles.
Users can create, inspect, edit, and delete map tiles.
Create management plans.
Plans belong to tiles and contain domain-specific activities.
Run simulations.
Simulation input is generated from tile assets and plan activities.
View and export results.
Users inspect biomass results and export a PDF report.

Current State

Real App Pieces To Keep

  • React/Vite shell with routed pages for map, tile, management plans, and simulations.
  • Mapbox/deck.gl map with persisted tile markers, tile outlines, activity polygons, and biomass overlays.
  • PocketBase collections for tiles, landcover, ocean data, plans, tasks, and simulations.
  • Tile creation and asset generation hooks, including Mapbox satellite/heightmap and worker-populated landcover/ocean assets.
  • Management plan and task CRUD for create/update, including polygon drawing and timeline display.
  • Simulation record creation and PocketBase endpoint /simulation/{id}/run that uploads tile assets and caches results.

Prototype Pieces Mixed In

  • Unused shadcn demo components and template docs/assets.
  • Visible controls with no behavior: import buttons, settings/history tabs, action buttons, and disabled video mode.
  • Hardcoded tile simulation info such as 128km2, 40x32, and Jan-Dec 2025.
  • Domain mismatch between terrestrial activity options and marine biomass simulation species.
  • Simulation pages show records, but do not yet behave like the management-plan index/detail flow.
  • No PDF export implementation yet.

Finish And Connect

These are the remaining implementation tasks required for the end-to-end app flow to feel cohesive.

P0: Plan Data Must Drive Simulation Input

Main gap: management-plan tasks are persisted, but the simulation runner currently uploads only landcover texture and depth. The task dates, areas, objectives, affected groups, cost/revenue, and biomass-change targets do not change the simulation.
  • Define the simulation-input contract for a management plan: activity timeline, polygon masks, affected species, fishing effort/policy changes, and any scalar options.
  • Transform managementPlans.tasks[].data into that contract before calling the upstream runner.
  • Decide whether polygon areas become JSON options, raster masks, modified texture/depth assets, or a separate upload part.
  • Store the exact normalized input used for a run on the simulations record so exports are reproducible.
  • Surface validation errors before a user can run: missing tile assets, unsupported activity type, unsupported species, incomplete area, or invalid dates.

P0: Computed Tile Details

  • Replace static Simulation info with values computed from tile fields, plan selection, and simulation options/results.
  • Candidate values: tile area from bbox, meters per pixel, asset readiness, number of plans, number of simulations, selected result grid size, timestep/sample interval, and result duration.
  • Hide sections that have no real data instead of filling with defaults.

P0: Tile Edit/Delete

  • Add edit support at minimum for tile name and visibility, with a clear save/cancel flow.
  • Add delete with confirmation, relation impact warnings, and post-delete route/cache cleanup.
  • Decide deletion semantics: block delete when plans/simulations exist, cascade them, or require explicit archive/delete of dependent records.

P0: Marine/Solver-Compatible Management Activities

  • Replace terrestrial activity types with domain selections that can be mapped to the simulator.
  • Recommended initial activity categories: fishingEffort, fishingClosure, speciesProtection, habitatRestoration, and monitoring if it is meaningful to the model.
  • Drive affected functional groups from the simulation species list or a shared domain config: plankton, sprat, herring, cod, plus age-group variants when enabled.
  • Use fields that map to simulation input, such as effort multiplier, biomass target, closure intensity, start/end step/date, and affected area.
  • Keep cost/revenue only if they appear in the PDF/business report or downstream analysis.

P0: Finish Action Buttons

  • Edit: route to edit the selected tile or selected management plan depending on context.
  • Results: route to the latest or selected simulation result for the active plan/tile.
  • Export: generate a PDF report for a completed simulation.

P0: PDF Export

  • Export should be available from a completed simulation result.
  • The PDF should include tile name/location, plan name, activity summary, simulation options, result metadata, biomass chart, selected species, and key result snapshots.
  • Recommended implementation: create a printable report route or server-rendered HTML report, then generate PDF from that view. This keeps the PDF layout testable and avoids duplicating report UI.
  • Store or regenerate exported PDFs from the simulation record, depending on whether exports must be immutable.

P0: Simulations Index And Routing

  • Replace the current basic /simulations list with a management-plan-style page.
  • Fetch simulations with expand: plan,plan.tile,plan.tasks.
  • Rows should show simulation status, tile, plan, created date, cached result availability, species/grid summary if available, and actions.
  • Clicking a row should route to /tile/:tileId/simulation/:simulationId.
  • Support empty, loading, error, and stale cached-result states.

P1: Result Viewing Polish

  • Remove the video mode and clarify the remaining result modes: map heatmap, 3D hex map, and biomass chart.
  • Make chart/map species filtering consistent and persist selected species in route or simulation UI state where useful.
  • Show a clear state when a simulation record exists but has not been run, when cached results are loading, and when a rerun will overwrite cached results.
  • Consider adding a "rerun" action with confirmation if simulation inputs changed after the cached result was produced.

P1: Data Model Cohesion

  • Decide whether tiles.simulations is still needed. Current lookup can derive simulations through simulation.plan -> managementPlan.tile.
  • Decide whether the old timesteps collection remains part of the app. The current result path uses cached resultJson/resultNpz files instead.
  • Add explicit simulation status fields if the UI needs reliable pending/running/failed/completed state rather than inferring from cached files.
  • Review public PocketBase create/update/delete rules before real users use the app.

Suggested Implementation Order

  1. Remove visible placeholders. Delete demo files, remove dead buttons/tabs/video, replace template docs/assets, and fix lint ignores.
  2. Make tile detail real. Computed tile details, edit/delete, and correct empty states.
  3. Normalize management-plan activities. Replace terrestrial mock selections with a typed marine activity model that maps to the simulator.
  4. Bridge plan to simulation. Generate and store normalized simulation input from plan tasks, then pass it to the runner.
  5. Upgrade simulation browsing. Implement the /simulations list/detail routing model and result state handling.
  6. Add PDF report export. Build a report route/template, generate PDF, and connect export actions.
  7. Hardening pass. Auth/rules review, deletion semantics, tests, fixtures, docs, and CI commands.

Open Technical Decisions

These should be settled before implementation of the plan-to-simulation bridge and PDF export, because they affect schema and route design.
  1. Exact upstream simulation contract for management-plan activities.
  2. Whether non-water or ocean-data-skipped tiles can be simulated, and what result type they should produce.
  3. Whether PDF exports are generated client-side, server-side, stored as files, or regenerated on demand.
  4. Whether historical simulation outputs should be immutable snapshots when a plan changes.
  5. Auth and permissions model for creating/deleting tiles, plans, tasks, simulations, and exported reports.
